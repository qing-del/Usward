# HTML 预览与 v1 设计接口对照检查

检查日期：2026-09-27。检查基线：`2a07c83`。本报告只记录检查结果，不修改设计文档、预览页面或业务实现。

## 1. 结论与检查范围

**预览版的主要业务流程在 `v1-design.md` 中都有对应的核心接口入口，没有发现整个业务模块缺失。设计目前还不能直接作为完整的前后端联调契约：有 8 类接口或数据契约需要补齐，另有 8 处预览逻辑与设计不一致或尚未覆盖。**

检查覆盖：

- 7 个 HTML 入口及其页面脚本、共用 `app.js`、预览说明。
- 77 个命名交互处理器，以及登录、弹窗表单和确认按钮的提交逻辑；处理器数量不等于需要实现的 API 数量。
- 设计的业务流程、权限、数据模型、时间与状态规则，以及第 11 节全部核心接口。
- 顺带核对 SQL 中与发现项直接相关的字段，以及 Java 工程的实际接口实现状态。
- 在隔离的 Node VM 中使用固定时间和模拟存储复现时间、提醒、首页、改期、取消等逻辑；未修改用户浏览器中的预览数据。

当前预览没有 `fetch`、`XMLHttpRequest` 或其他 API 调用，业务状态保存在 `localStorage`。Java 主源码目前只有应用启动类，没有业务 Controller/Service/Mapper。**下文的“有对应接口”指设计文档已列出接口，不能理解为后端已经实现。**

对照依据：[设计文档](./v1-design.md)、[预览边界说明](../static/UI/README.md)、[共用交互逻辑](../static/UI/assets/app.js)、[数据库初始化](../static/database/initDatabase.sql)。

状态含义：

- **已覆盖**：业务规则和接口入口都能对应；具体 DTO 仍需按后文补齐。
- **契约待补**：已有接口可承载，但文档未定义足够的参数、返回字段或状态处理。
- **读取能力待补**：当前核心接口表没有明确覆盖该读取行为，可扩展已有 DTO，也可增加读取接口。
- **纯前端**：展示、导航、草稿或演示工具，不需要新的业务接口。
- **预览待补**：设计已有能力，预览没有完整体现，或预览逻辑有偏差。

以下路径均省略 `/api/v1` 前缀；表中的参数和 DTO 建议不是当前文档已经确定的契约。

## 3. 需要补齐的 8 类接口或数据契约

P1 表示会阻碍准确持久化或核心流程联调；P2 表示需要在实现前约定列表、聚合或交互细节。没有把纯演示实现当成缺失的业务接口。

### G01 · P1 · 内置头像选择缺持久化字段

- 预览 `me.js:18` 允许选择昵称字、小花、小太阳、新芽，存入 `user.avatar`；设计 §2.1 只说明头像使用内置样式，§10 的 `app_user` 未列头像字段。SQL 的 `app_user` 第 12–26 行也没有该字段。
- `PATCH /me` 路径已经存在，**缺的是头像选择的正式模型和请求/响应字段**。不能仅凭昵称推导出用户已选择的花或太阳。
- 建议定义 `avatarStyle` 的允许值，在 `GET/PATCH /me` 中读写，并在连接和分享者的公开资料中返回；昵称字可按昵称派生。固定样式无需上传文件接口。

### G02 · P1 · 承诺“只有日期”与 `due_at` 不一致

- `app.js:358–359` 允许填写截止日期而不填写具体时间；此时保存 `due='2026-09-28'`、`dueAt=''`。设计 §10 和 SQL `commitment.due_at` 只有 UTC 时间戳，没有日期截止或精度字段。
- 直接按模型传 `dueAt` 会丢掉日期截止；任意补一个时刻又会影响“今天到期”、过期判定、时区切换和再次编辑时是否显示具体时间。
- 需要二选一并写清：正式 UI 只接受精确截止时间；或支持日期截止，并约定日期、截止精度、判断时区及当天边界。若用当天结束的绝对时间表示，也要解决日期精度如何回显。`POST/PATCH /commitments` 已可承载，不一定增加接口。

### G03 · P1 · 自己的有效连接邀请读取与口令重显未闭合

- `me.js:6、15、23–29` 从本地数据取已有有效邀请；刷新后仍可“查看我的邀请”，重复显示相同口令、到期时间并撤销。
- §11 有生成、预览收到的口令、接受、撤销，但没有明确查询本人当前有效邀请的行为。`GET /connection` 是否包含未连接者的待发邀请也未定义。
- §2.2 要求服务端只保存口令哈希，因此不能从数据库重新取回同一明文口令。后端只保存哈希是正确的，不应为配合预览改成明文保存。
- 建议创建成功只返回一次 `{id, token, expiresAt}`；通过 `GET /me`/`GET /connection` 的邀请元数据，或增加 `GET /connection-invites/current`，返回自己的 `{id, status, expiresAt}`。刷新后展示状态、撤销或重新生成；若仍需重复展示口令，必须另行明确客户端临时保留口令的行为。

### G04 · P1 · 提醒能写，读取、回显与取消所需标识未定义

- `app.js:247、251–253、309、312、358、366` 和承诺侧栏需要取得“当前用户对该资源的提醒”，包括对方分享卡片与双方共同事件。§11 只列 `PUT /reminders` 和 `DELETE /reminders/{id}`，未列读取接口，也没有定义资源 DTO 中是否包含自己的提醒。
- 不能把作者的 `reminder` 返回给所有读取者。每个读取者都应取得自己的 `{id, scheduledAt, revision, status}`；无提醒返回 `null`。拿到提醒 ID 后才能在刷新后可靠调用 DELETE。
- 建议在卡片/事件/自己的承诺详情中返回 `myReminder`，在首页/提醒侧栏返回自己的提醒摘要；或定义按资源查询提醒的 GET。两种方式选定其一即可，不能据缺少 GET 就断言必须增加独立接口。
- 还需约定 PUT 的 `resourceType/resourceId/scheduledAt`，清空表单如何取消、相同时间重新设置如何增加修订号，以及完成/取消资源后的提醒清理行为。新建资源并设置提醒时，是业务接口一起处理还是先创建再 PUT，也需明确；后者失败时应保留已创建资源并重试提醒，避免重建重复内容。

### G05 · P1 · 冲突提示与“仍然接受”缺请求/响应契约

- `app.js:332、337、351` 在打开邀约和点击接受时计算两人的安排冲突。正式前端不应为了计算这些冲突下载对方的私密事件。
- §6.2 已规定仅提示冲突时间且允许确认仍接受，但 §11 没有确定由邀约详情还是预检查接口返回冲突，也没有确定接受请求如何携带明确确认。
- 建议扩展邀约详情返回脱敏 `conflicts` 时间段；接受请求包含类似 `confirmConflicts` 的标记。接受事务内再次检查冲突，有新增未确认冲突时返回明确错误码和脱敏范围，确认后重试。具体错误码/HTTP 状态需写入契约，不能混用普通版本冲突文案。
- 共同改期接受复用同一规则，并排除目标原事件自身；不能把对方标题、备注、个人事件真实 ID 或任意对象完整 DTO 放进冲突结果。无需为此强制增加新路径。

### G06 · P2 · 列表筛选、分页、统计和首页分组未定义

- `memories.js:5、12、16、21` 需要范围、归档、关键词、类别、标签、排序、全量匹配数和可访问标签集合；`expressions.js:7–9、15` 需要方向、状态、最近回应、回应数；`commitments.js:6–12` 需要作者范围、状态、截止排序和各状态总数。
- §11 只有默认 20/最多 100 的限制，没有参数名、分页结构或全量计数。客户端对首批 20 条做筛选，不能替代服务端权限范围内的搜索，也不能正确生成全量标签/数量。
- 建议给现有列表接口补齐 `scope/status/archived/keyword/category/tag/sort/page/size` 中适用的参数，以及类似 `{items, total, page, size, hasMore}` 的结构。标签聚合、状态数量可以随列表或首页/资料统计返回，不必每项另加 API。
- `GET /calendar`、`GET /availability` 要明确范围参数、边界是否包含、查询时区及取消事件是否返回；三种视图都按可见范围查询。`GET /dashboard` 要明确自己的今日日程、待处理数量、提醒范围、到期/逾期承诺、展示上限及排序。
- 评论已有独立 GET；表达详情中的回应历史则需明确完整返回、截断或分页获取的方式。当前没有单独的回应 GET，不代表一定缺接口，但列表 DTO 不能被假定自动包含全部回应。

### G07 · P2 · 全量未读数量与“全部已读”的范围未定义

- `app.js:141、375–379` 从本地全部可见通知算未读数，并一次标记所有可见通知。列表分页后，只数当前页会少算，只标记当前页也不等于预览的“全部”。
- `GET /notifications` 可以增加经过资源权限过滤的 `unreadCount`；也可在已有首页 DTO 返回，明确 60 秒刷新时使用的来源。没有必要仅为计数必然增加新 GET。
- “全部标为已读”可通过遍历分页调用现有单条 read 实现，所以不属于无法实现的功能。若采用批量处理，建议增加 `POST /notifications/read-all`，明确只处理当前用户仍可访问的通知，并确定本次操作的时间边界，避免把操作期间刚到达的通知意外标为已读。

### G08 · P1 · 资源 DTO、字段映射与版本传递尚未成为正式契约

§10 给了表，§11 给了路径和 `expectedVersion` 总原则，但没有定义各资源的 DTO 和各共享操作到底携带哪个版本。预览数据不能原样作为请求体或服务端响应。

| 预览数据 | 正式接口必须明确的映射/限制 |
| --- | --- |
| `owner/sender/author = 'me'/'partner'`，`signedIn` | 由 Session 和服务端真实 `ownerId/senderId/recipientId/authorId` 判定；不能信任客户端相对身份或登录布尔值 |
| `m-...`、`e-...` 等演示 ID | 服务端 BIGINT ID 按字符串传输，客户端仅作展示和引用 |

## 4. 设计已有支持，但预览需要调整的 8 处

以下属于预览覆盖或实现偏差，不应靠新增后端接口来掩盖。

### U01 · P1 · 夏令时切换日的本地时间转 UTC 会偏移一小时

- 位置：`app.js:116–121`，`fromLocal` 只按一次假定 UTC 时刻求偏移；`me.js:3` 又允许纽约/伦敦这类有夏令时的时区。
- 隔离复现：纽约输入 `2026-03-08T03:30`，转换后回显 `04:30`；输入 `2026-11-01T02:30`，回显 `01:30`。这两个输入都不是当地重复/不存在时间，仍会错误转换。
- 影响所有时间输入：安排、邀约、改期、精确截止时间和提醒。按 §10 的时间规则，应使用正确的时区转换，并约定重复/不存在当地时间的处理方式。

### U02 · P1 · 切换显示时区后编辑全天安排，会悄悄改变创建时区

- 位置：`app.js:299–301`。个人事件编辑总是写入 `eventTimezone=state.user.timezone`，并重新计算全天绝对边界。
- 隔离复现：上海创建的 `2026-09-28` 全天安排，开始边界为 `2026-09-27T16:00Z`。把显示时区改为纽约，再保存同一天的安排，创建时区变成纽约，开始边界变成 `2026-09-28T04:00Z`。
- 与 §6.2、§10 的全天创建时区边界，以及 `me.js:19` 的“调整显示时区不会改变已记录时间”说明不一致。编辑应保留原时区，或显式让用户提出时区变更；不能因改变显示偏好而默默修改。
- 全天对象同时保留 UTC 起止和日期字段是本地模型的做法；接正式接口时需按 G08 转成互斥 DTO。

### U03 · P2 · 首页私人提醒只取一张自己的记忆卡片

- 位置：`today.js:9、18`。用 `find` 取第一张 `owner='me' && reminder` 的卡片，不筛时间或触发状态、不排序。
- 对方已分享卡片上由本人设置的提醒、个人/共同事件提醒、自己的承诺提醒都不在此分组；即使已有这些提醒，仍可能显示“还没有设置提醒”。陈旧或很远的第一张卡片也可能挡住更相关的提醒。
- 已隔离复现“共享卡片 + 个人事件 + 承诺均有自己的提醒，首页仍称未设置”。§3、§7.2 和 `GET /dashboard` 已支持私人提醒，需修正首页聚合逻辑和范围。

### U04 · P2 · 首页按日期判断承诺逾期，忽略具体截止时刻

- 位置：`today.js:19`；正确的共用判断在 `app.js:97`，承诺页已使用它。
- 隔离复现：当前为 `2026-09-27 15:00` 上海时间，承诺截止为同日 `14:00`；`U.overdue` 为 true，首页仍显示“今天到期”，没有“已过约定时间”。
- 应统一使用精确截止判断，同时明确首页承诺排序和到期范围；§7.1 与已有承诺接口不需要更改路径。

### U05 · P2 · 提醒取消后用相同时间重新设置，不会形成新计划

- 位置：`app.js:162–169、251–253、312、359`。去重只比较 `firedReminder === reminder`，取消或重设时没有增加修订号。
- 隔离复现：一个过去时刻的提醒触发一次，取消后再设成相同时刻，通知仍为 1 条；新设置被当作旧计划已发送。
- §7.2 已规定编辑增加 revision，旧计划失效。预览若继续演示重设行为，应以计划修订去重；正式后端使用现有提醒表和事务规则实现。

### U06 · P2 · 共同取消的说明未展示，通知没有资源引用

- 位置：`app.js:315` 保存 `cancelReason`，但 `eventDetail` 第 309 行不渲染它；同处生成 `kind='system', resourceId=''` 的通知。
- 隔离复现：输入“测试取消说明”，数据保存了该说明，取消后双方详情不显示；另一方只收到不可打开事件的通用通知。
- §6.3 的取消说明已支持，`POST /events/{id}/cancel` 已存在。应在取消事件详情显示说明，并让取消通知引用该事件，按当前连接重新鉴权。设计 §7.2 和 SQL `notification.resource_type/resource_id` 要求有效引用，不能把空引用通知直接搬进后端。

### U07 · P2 · 改期后只检查接受者当前加载的提醒

- 位置：`app.js:343–348`。只有接受者的 `e.reminder` 非空时发送“请检查自己的提醒”；另一方的 `privateReminders` 不参与检查。
- 隔离复现：提议者设置了提醒，接受者没有提醒；接受修改后，提议者只有“对方接受了你的提议”通知，没有检查原提醒的提示。
- §7.2 已要求事件改期后提示用户检查，提醒时间不自动变化。应分别向有提醒的两位用户提供提示，或在各自再次打开事件时提示，且不向对方泄露提醒时间。

### U08 · P2 · 承诺只实现表达来源，卡片/事件来源入口缺失

- 位置：`app.js:289、356–360、364–366`。当前可达入口只传 `sourceType='expression'`；承诺表单没有卡片/事件来源选择，也没有相应转换按钮。
- 详情又把一切非 expression 来源都当作 memories 查找，未来接入事件来源也会打不开。
- §7.1 明确允许关联表达/卡片/事件，§10 和 SQL 已有多态引用；已有 `POST/PATCH /commitments` 及三个资源的详情接口可实现。需要补 UI 入口和按来源类型读取，不能判为缺一个“转换成承诺”接口。

## 5. 不应算作接口缺失的预览行为

| 行为 | 正式实现方式 |
| --- | --- |
| 各种导航、视图切换、装饰、弹窗、密码显隐 | 前端交互；需要数据时复用已有查询 |
| 保存输入草稿、失败后保留输入 | 客户端按账号隔离草稿；设计没有要求草稿跨设备同步 |
| 分享前整卡预览 | 读取作者最新卡片，展示后调用 share；版本变化需处理，不必新增分享预览接口 |
| 从表达写下一步或发起邀约 | 已有创建接口 + 来源引用，不能自动给另一方创建任务或确认邀约 |
| 两次解除确认 | 两个前端确认步骤后调用一次解除接口 |
| 本地示例数据、任意演示密码、两账号视角切换、载入示例 | 预览工具；正式身份由独立 Session 登录取得 |
| 浏览器每分钟模拟生成提醒通知 | 原型模拟；正式版由服务端扫描器生成，网页只刷新自己的通知/数量 |
| `GET /calendar` 不返回对方完整个人事件 | 正确的权限边界；对方忙闲应来自脱敏的 availability DTO，冲突由服务端计算 |

## 6. 补齐顺序与联调验收

建议先决定 G01–G05 的模型与行为，再补 G06–G08 的具体 DTO/查询/版本约定，同时修正 U01、U02 的时间问题。其余预览偏差可以在接对应页面时一并处理。

最小契约补充范围：

1. 账号 DTO：昵称、内置头像、时区、自己的共享开关；连接 DTO：连接 ID、状态和双方允许公开的资料。
2. 连接邀请：创建时返回一次口令；本人有效邀请元数据的读取和撤销；preview/accept 的错误状态。
3. 承诺：日期截止的明确规则，来源类型和权限；截止变更通知与结果字段。
4. 提醒：自己的读取/回显、PUT 请求、revision、取消语义和资源变更后的清理；不能返回另一方设置。
5. 邀约和共同事件：两种时间结构、脱敏冲突、明确确认、期望版本、接受返回的事件、取消说明。
6. 列表与首页：各筛选、排序、分页、统计及全量未读数；全部已读采用单条组合或批量操作。
7. 写入响应与异常：最新资源/版本、400/401/404/409 的具体码；真实请求失败保留草稿。

后续正式接口应覆盖的验收场景：

- 未连接者仍能完成个人卡片、日程、承诺、提醒和首页流程；刷新后数据来自服务端。
- 超过 20 条的数据，搜索、标签、方向/状态筛选、加载更多、数量和“全部已读”仍正确。
- 双人从表达到回应、邀约、确认、改期；接受前原时间保持不变，同一邀约重试不重复创建事件。
- 对方无论是否共享忙闲，邀约冲突提示都只含允许展示的时间范围；更换任意 ID 也不能越权。
- 每人只读写自己的提醒；共同事件两方提醒互不影响；取消后重设相同时刻产生新修订；扫描重试和重启不重复触发同一修订。
- 纽约/伦敦夏令时边界正确转换；修改显示时区不会改变全天安排的创建边界；承诺日期截止正确回显。
- 撤回、删除、撤销分享、解除连接后，资源详情、来源引用、通知与提醒入口都不能继续访问；新连接不继承旧空间。
- 改期后双方检查自己的提醒；取消说明可读取；卡片和事件可作为承诺来源，来源不可访问时正确降级。
